# 画面质量阈值与远程会话结果联调说明

核对日期：2026-09-22。范围：当前 FirmwareUpgrade 源码、工作区 Device-Management 副本、板子 `10.8.30.54` 和 Cloud `10.8.30.64:8080` 的只读查询。本次只更新文档，没有修改前端或后端业务代码，没有部署 Detector 或重建 Agent/Cloud。

## 给前端的画面异常边界

当前 `picture_metrics` 的四个数值都是 **0～100 的异常分数，越大越异常**，保留一位小数。不是异常布尔值、异常概率、暗像素占比、遮挡面积比例或原始清晰度。统一按 **分数 >= 80 判异常，分数 < 80 判正常**，不要使用 `if (value)`、`value > 0`，也不要对接口 `blur` 使用原始拉普拉斯方差的反向判定。

| Cloud HTTP 字段 | 展示名 | 异常条件 |
|---|---|---|
| `picture_metrics.blur` | 模糊异常分数 | `blur >= 80` |
| `picture_metrics.black_screen` | 黑屏异常分数 | `black_screen >= 80` |
| `picture_metrics.occlusion` | 遮挡异常分数 | `occlusion >= 80` |
| `picture_metrics.brightness_abnormal` | 亮度异常分数 | `brightness_abnormal >= 80` |

单项展示参考代码（交给前端接入，本仓库不修改页面）：

```javascript
function metricState(channel, key) {
  const value = channel?.picture_metrics?.[key];
  if (channel?.status !== 'running' ||
      typeof value !== 'number' || !Number.isFinite(value) ||
      value < 0 || value > 100) {
    return 'unknown';
  }
  return value >= 80 ? 'abnormal' : 'normal';
}
```

`0` 是有效正常值；缺失、`null`、非数值、越界值和无有效运行画面显示“未知/暂无数据”。设备离线或 `observed_at` 已过期时也不能继续把缓存值当作实时正常结果，过期策略应与页面轮询和设备状态策略一致。老版本计算失败可能返回四个 0，前端无法仅靠这四个数识别失败，应结合版本与有效画面状态。

例子：`blur=8.8`、`79.9` 都正常；`80.0`、`95.0` 异常。这里的“正常”表示未达到当前阈值，不是经过标定的图像质量保证。

## 后端实际计算方式

计算发生在 Python Detector 的 `calculate_picture_metrics()`，Go Agent 和 Cloud 负责传递、缓存这些值。对解码后的 BGR 帧使用 `cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY)` 获得 0～255 灰度图，定义：

- `μ`：整帧灰度均值，`np.mean(gray)`。
- `σ`：整帧灰度标准差，`np.std(gray)`。
- `V`：拉普拉斯响应方差，`cv2.Laplacian(gray, cv2.CV_64F).var()`。

| 指标 | 分数公式（之后上限截到 100，保留一位小数） | 分数 80 对应的原始量边界（未考虑舍入） |
|---|---|---|
| 黑屏 | `max(0, 100 - 2μ)` | `μ <= 10` |
| 遮挡 | `max(0, 100 - 2σ)` | `σ <= 10` |
| 模糊 | `max(0, 100 - V)` | `V <= 20` |
| 亮度异常 | `μ < 40` 时 `(40-μ)*2.5`；`μ > 215` 时 `(μ-215)*2.5`；其余 0 | `μ <= 8` 或 `μ >= 247` |

原始 `V` 越大通常越清晰，但接口输出 `blur=max(0,100-V)`，方向已经反转。前端应直接比较后端返回的四舍五入分数，不自行还原原始量。

仓库 `picture_quality_status()` 使用相同的 `>=80` 边界，汇总状态按 `black_screen → occlusion → blur → brightness_abnormal` 的顺序选择首个异常，否则为 `normal`；没有指标时为 `unknown`。单项可以同时异常，例如纯黑图的四个分数都是 100，但汇总只显示 `black_screen`。这些是单帧统计启发式，不含时间窗口、连续帧确认或故障概率模型；低纹理、暗光等场景可能同时触发多项，后续标定需使用真实场景样本。

Detector 协议字段为 `pictureMetrics`、`qualityStatus`；Cloud HTTP 通道接口 `GET /api/v1/devices/{id}/video-channels` 返回 `picture_metrics`、`quality_status`。不要混用两层字段名。

## 远程会话的执行结果能否只由前端实现

结论取决于要展示实时输出、整场历史输出，还是逐条命令结果：

| 需求 | 当前能力 | 最小改动位置 |
|---|---|---|
| 在打开的终端实时显示命令输出 | 已有 `output.data` 流 | 前端消费现有 WebSocket，无需新增 Go 接口 |
| 仅在同一浏览器暂存本次会话输出 | 前端可以缓存当前收到的数据 | 前端可做，但不能补回过去未保存的历史，不等于服务端会话记录 |
| 关闭会话后、刷新/换浏览器后查看历史输出 | 管理平台 Node Gateway 已实现有界脱敏持久化，尚未部署 | 执行迁移并发布 Node API；前端调用现有会话详情接口 |
| 历史表逐条显示命令、耗时、退出码、成功/失败及输出 | 当前协议没有逐命令边界和结果 | 先增加 Shell 集成/结构化执行协议，再由后端落库，前端按结果展示 |

用户描述的“查看详情 → 远程会话 → 历史会话 → 命令明细”属于后两种，不能靠前端简单补一个字段实现准确结果。

### 已核实的数据链路与缺口

1. Agent `cmd/agent/terminal.go` 将 PTY 读取的数据按块发送 `terminal.output`，包含 `session_id`、`sequence`、`data`。`input` 是终端输入片段，可能只是一个按键，不能当作完整命令。
2. Go Cloud `cmd/cloud/terminal.go` 转成浏览器 JSON：`{"type":"output","session_id":"...","sequence":1,"data":"..."}`。这里的 `data` 是文本，浏览器不需要 Base64 解码；Go 内部 `[]byte` 的编码不等于浏览器协议。
3. `Device-Management/api/app/lib/service/terminalGateway.js` 继续原样转发实时数据，通过 `terminalRecording.js` 对副本脱敏后持久化。旧版把输入前 500 字符直接写 `SystemLog` 的路径已删除。
4. `EdgeRemoteSession` 新增可空 `recording JSONB`。现有列表返回 `recordingSummary`；现有详情额外返回 `commands` 和 `recording`。旧记录明确返回未录制，不伪造历史。接口字段和迁移脚本见 [远程会话持久化与脱敏接口设计](远程会话持久化与脱敏接口设计.md)。
5. 当前前端副本的 `SessionHistoryDrawer` 读取 `session.commands`，而 `toSession()` 没有保留该字段；点击历史项直接展示列表记录，没有调用已有的详情 action。即便后端新增数据，前端仍需接详情接口和保留字段。

`exited.exit_code` 是 **整个 Shell 进程的退出码**，不是每条命令的退出码；`error` 是终端/网关错误，也不能代表上一条命令执行失败。Linux PTY 输出混合了 stdout、stderr、输入回显、提示符和 ANSI 控制字符，不能按一条 WebSocket 消息、一行文字或一段无输出时间切分命令。交互程序、多行输入、管道、后台任务都会破坏这种推断。

### 后端建议与交接边界

已按确认范围在 **Device-Management 的 Node Gateway** 实现脱敏输入和会话输出，复用本地会话 ID 与 Cloud 会话关联。记录使用网关自己的事件序号和接收时间，首版采用单会话有界详情返回，不新增分页路由。上限为 1 MiB / 5000 事件，截断或异常标记为 partial。页面显示“会话输出”，不要用终端总退出码生成每条命令的成功记录。

如果必须保留当前“命令/耗时/退出码/结果”表语义，需新增明确的 `command_id`、命令开始/结束时间、逐命令退出码和输出关联机制。例如限定 Bash 时做 Shell 集成，或增加独立的单次命令执行协议；这涉及后端能力和协议设计，不能仅对现有 PTY 文本做前端解析。耗时由执行端时间计算，浏览器收包间隔不能当作执行耗时。旧会话没有保存的输出和退出码无法追溯补齐。

本次保留完整交互终端，不增加逐命令执行协议、平台鉴权接口或端口。历史 `commands` 是可识别的提交输入，状态为 `submitted`，逐命令耗时和退出码为 null；无法识别的交互输入隐藏。前端仍需对接详情并保留字段。运维目的已由 `purpose` 保存/返回，列表标题应由前端优先显示该字段。
