# 事件告警、设备重启和 RTSP 测试接口

更新日期：2026-09-22。OpenAPI 版本：0.7.1（本次仅补充部署授权，接口契约不变）。

## 实现分工

按本次确认，“事件”和“告警”指同一套 Detector 检测记录，先提供查询，不增加确认、处理或关闭流程。

链路为：Detector 产生检测事件 → Agent 写本地 SQLite 和图片 → Agent 向 Cloud 上报 → Cloud 持久化并确认 → Agent 更新已上报标记。断网时 Agent 保留未上报记录，恢复后继续补报。页面查询 Cloud 中已接收的记录，因此设备离线时仍能查询历史；设备尚未上传的数据不会提前出现在 Cloud 页面。

设备重启和 RTSP 探测由 Agent 在设备上执行。Cloud 负责请求关联、状态码和操作结果查询；管理 HTTP 接口不要求额外凭证，业务账号和权限沿用现有管理平台。设备通信仍使用原有设备 Token。上游 `/edgeCloud` 代理仍需增加对应路由并转发状态码。

## 事件与告警查询

| 方法 | 路径 | 返回 |
|---|---|---|
| GET | `/api/v1/events` | 分页检测记录 |
| GET | `/api/v1/events/statistics` | 筛选范围内统计 |
| GET | `/api/v1/events/{deviceID}/{rowID}` | 单条详情 |
| GET | `/api/v1/events/{deviceID}/{rowID}/image` | JPEG 图片 |
| GET | `/api/v1/alarms?page=1&page_size=30` | 相同记录的分页结果 |
| GET | `/api/v1/alarms/statistics` | 相同统计 |
| GET | `/api/v1/alarms/{deviceID}/{rowID}` | 相同详情 |
| GET | `/api/v1/alarms/{deviceID}/{rowID}/image` | 相同图片 |

记录主键是 `(device_id, agent_row_id)`，不同设备可以有相同的 row ID。重复上报不会生成重复记录。事件时间和置信度在接收时校验。

列表和统计共用筛选条件：

| 参数 | 含义 |
|---|---|
| `device_id` | 设备 ID 精确匹配 |
| `channel_id` | 通道 ID 精确匹配 |
| `detection_type` | 检测类型，如 `landslide` |
| `start_time` / `end_time` | 事件发生时间范围，包含边界；RFC3339，必须有时区 |
| `min_confidence` | 最小置信度，0～1 |
| `page` | 页码，默认 1，最大 1000000，仅列表使用 |
| `page_size` | 每页条数，默认 30，最大 200，仅列表使用 |

分页按实际事件时间倒序，再按设备 ID 和记录 ID 稳定排序。总数和页面读取同一数据库快照。发生新事件后页码可能移动，刷新列表即可。带 `+08:00` 的时间需要 URL 编码，将 `+` 写作 `%2B`。

分页响应示例：

```json
{
  "items": [{
    "device_id": "DEVICE-001",
    "device_name": "边坡设备",
    "agent_row_id": 12,
    "channel_id": "CH-01",
    "detection_type": "landslide",
    "confidence": 0.91,
    "alarm_time": "2026-09-21T12:00:00+08:00",
    "received_at": "2026-09-21T04:00:01Z",
    "image_url": "/api/v1/alarms/DEVICE-001/12/image"
  }],
  "total": 1,
  "page": 1,
  "page_size": 30,
  "has_more": false
}
```

图片通过独立请求获取，不把 Base64 放入列表。没有图片时省略 `image_url`；图片或记录不存在返回 404。查询参数不合法返回 400。

统计返回 `total`、`with_image`、`device_count`、`first_alarm_time`、`last_alarm_time` 和 `by_detection_type`。类型分组最多 50 种，按数量倒序；`total` 是完整匹配总数。空集时间为空字符串、数量为 0。

兼容旧页面：`GET /api/v1/alarms?limit=30` 不传 `page/page_size` 时仍返回旧数组，并按 Cloud 接收时间倒序；现有管理页面无需立即改造。新页面建议使用 `/events` 的统一分页响应。

## 重启设备

```http
POST /api/v1/devices/{id}/reboot
Idempotency-Key: <一次操作对应的固定UUID>
Content-Type: application/json

{"confirm":true}
```

Agent 配置显式设置 `"allow_remote_reboot": true` 才允许执行。示例配置保持 false；仅支持 Linux/systemd，通过固定参数 `systemctl reboot --no-block` 重启设备操作系统，Agent 的运行用户必须具备该权限。不接受命令字符串、可执行路径或额外参数。

这里有两个独立条件：配置开关允许 Agent 接受指令，操作系统授权允许运行用户执行重启。`kickpi` 加入 sudo 组、能够手动输入 sudo 密码，不代表后台 Agent 已获得无交互重启权限。当前程序直接调用 `systemctl`，不会调用 `sudo` 或自动输入密码；单独配置 `sudoers` 的免密命令也不会被当前调用使用。请完成下方部署授权后再测试。Cloud 管理接口不额外要求凭证，与这项 Linux 权限无关。

Agent 先写持久化回执、再应答、延迟约 2 秒后执行；应答发送失败则不执行。正在下发升级文件时拒绝重启，重启已接受后拒绝开始新升级。不同 Cloud 连接或 Agent 进程中的重复请求，也通过同一操作 ID 的 SQLite 回执去重。

接受后返回 HTTP 202：

```json
{
  "id": "操作ID",
  "device_id": "DEVICE-001",
  "type": "reboot",
  "status": "accepted",
  "message": "device accepted reboot; waiting for a new boot heartbeat",
  "created_at": "2026-09-21T04:00:00Z",
  "updated_at": "2026-09-21T04:00:01Z"
}
```

随后轮询：`GET /api/v1/devices/{id}/operations/{operationID}`。设备断线或重连本身不是成功证据，只有上报新的 Linux `boot_id` 才转为 `succeeded`。

| 状态 | 含义 |
|---|---|
| `requested` | Cloud 已登记，等待设备确认 |
| `accepted` | 设备接受，等待新启动标识 |
| `unknown` | 应答或执行结果不确定，需要查询/重试原操作 |
| `failed` | 明确拒绝、执行失败或进程中断导致未执行 |
| `succeeded` | 设备恢复并上报不同的系统启动标识 |

相同设备、相同 `Idempotency-Key` 返回同一操作；重复点击不创建新任务。超过 10 秒的 `requested/unknown` 使用**原 key** 重试，会重新发送同一个操作 ID，由 Agent 回执阻止重复执行。未解决操作会阻止新 key 创建另一条重启任务。旧操作的状态不能仅因断线、超时或 Cloud 重启就改成成功。

状态码：参数错误 400、Agent 禁止重启 403、设备不存在 404、执行升级/重启冲突 409、不支持的设备平台 422、设备明确失败 502、设备离线 503、应答超时 504。设备离线时不新建延迟重启任务。504 响应包含操作 ID，不能通过更换 key 盲目再次执行。

如果 Agent 进程在延迟执行前退出，重新启动同一系统时会把该回执标为 `failed/interrupted`，不会启动后突然补执行重启。系统命令结果不确定时保留 `unknown`；需要运维确认系统状态，不自动循环重启。

### 板端部署与重启授权

适用示例：Ubuntu/systemd、账号 `kickpi`、安装目录 `/home/kickpi/testAgent`、服务 `agent_watchdog.service`。Agent 以普通用户运行；安装系统服务和 Polkit 文件的命令使用 sudo。下列步骤不会重启整机，但服务安装步骤会短暂重启 Agent。使用其他账号或目录时，需同步修改服务模板、授权规则和命令。

**1. 开启配置并保留其他字段。** 在板子执行：

```bash
cd /home/kickpi/testAgent
cp -p configs/agent.example.json configs/agent.example.json.bak-$(date +%Y%m%d-%H%M%S)
python3 - <<'PY'
import json
from pathlib import Path
p = Path('configs/agent.example.json')
config = json.loads(p.read_text())
config['allow_remote_reboot'] = True
p.write_text(json.dumps(config, ensure_ascii=False, indent=2) + '\n')
PY
```

**2. 安装普通用户服务。** 将仓库 `script/agent_watchdog.service` 和 `script/49-agent-reboot.rules` 复制到板子 `/home/kickpi/testAgent/script/` 后执行：

```bash
cd /home/kickpi/testAgent
# 已部署服务先留备份；首次安装没有该文件可跳过此行。
sudo cp -p /etc/systemd/system/agent_watchdog.service \
  /etc/systemd/system/agent_watchdog.service.bak-$(date +%Y%m%d-%H%M%S)
sudo install -o root -g root -m 0644 script/agent_watchdog.service \
  /etc/systemd/system/agent_watchdog.service
sudo systemctl daemon-reload
systemctl cat agent_watchdog.service
```

模板显式设置 `User=kickpi`、`Group=kickpi`、工作目录和绝对配置路径，并在 `network-online.target` 之后启动。已有 drop-in 仍会覆盖主服务文件，应检查合并结果。确认配置、状态文件、数据库目录和日志目录可由 `kickpi` 读写，不要为此递归修改整个系统目录的属主。

若还有手动启动的 Agent，应先核对进程再终止那个进程，避免抢占 `127.0.0.1:8085`；不要同时启动两个 Agent：

```bash
ps -eo user,pid,ppid,args | grep '[a]gent-linux-arm64'
# 仅在确认目标是手动启动的旧 Agent 后执行：kill -TERM <实际PID>
sudo systemctl enable agent_watchdog.service
sudo systemctl restart agent_watchdog.service
systemctl show agent_watchdog.service -p User -p Group -p MainPID -p ActiveState -p SubState
sudo journalctl -u agent_watchdog.service -n 40 --no-pager
```

必须看到 `User=kickpi`、`ActiveState=active`、`SubState=running`，并确认 Cloud 连接恢复。仅 `enable` 不会立即启动服务；显式 `systemctl stop` 后，即使 `Restart=always` 也不会自动拉起，应使用 `start` 或 `restart`。

**3. 安装限定动作的 Polkit 授权。** `script/49-agent-reboot.rules` 内容为：

```javascript
polkit.addRule(function(action, subject) {
    if (subject.user === "kickpi" &&
        (action.id === "org.freedesktop.login1.reboot" ||
         action.id === "org.freedesktop.login1.reboot-multiple-sessions")) {
        return polkit.Result.YES;
    }
});
```

该规则授权范围是 **kickpi 账号的所有进程，包括 SSH 会话**，并非只授权 Agent。普通重启和多会话重启分开授权，是为了同时连接多个 SSH 会话时仍能测试。规则不授权关机、忽略 inhibitor 的重启、任意 systemd 服务管理；不应添加广泛的 `manage-units` 或通配授权。板端 D-Bus/Polkit 组合不保证提供 `subject.system_unit`，不要直接添加该条件，否则可能造成规则无法匹配。

```bash
cd /home/kickpi/testAgent
sudo install -d -m 0755 /etc/polkit-1/rules.d
if sudo test -f /etc/polkit-1/rules.d/49-agent-reboot.rules; then
  sudo cp -p /etc/polkit-1/rules.d/49-agent-reboot.rules \
    /etc/polkit-1/rules.d/49-agent-reboot.rules.bak-$(date +%Y%m%d-%H%M%S)
fi
sudo install -o root -g root -m 0644 script/49-agent-reboot.rules \
  /etc/polkit-1/rules.d/49-agent-reboot.rules
sudo journalctl -u polkit.service --since '2 minutes ago' --no-pager
```

Polkit 会监视并重新加载规则文件，无需重启板子或 Agent 来加载授权。确认日志没有规则语法错误。配置开关仍需重启 Agent 才生效。

**4. 只读验证授权，不能用实际 reboot 命令代替检查。** 用 `kickpi` 执行以下命令，不加 sudo、不允许交互认证：

```bash
agent_pid=$(systemctl show agent_watchdog.service -p MainPID --value)
test "$agent_pid" -gt 0 || { echo 'Agent is not running'; exit 1; }
# PID + 启动时间 + UID 标识当前进程，避免只传 PID 的复用歧义。
agent_subject=$(python3 - "$agent_pid" <<'PY'
import os, sys
from pathlib import Path
p = Path('/proc') / sys.argv[1]
fields = (p / 'stat').read_text().rsplit(')', 1)[1].split()
print(f'{sys.argv[1]},{fields[19]},{os.stat(p).st_uid}')
PY
)
for action in org.freedesktop.login1.reboot org.freedesktop.login1.reboot-multiple-sessions; do
  pkcheck --action-id "$action" --process "$agent_subject"
  echo "$action exit=$?"
done
busctl call org.freedesktop.login1 /org/freedesktop/login1 \
  org.freedesktop.login1.Manager CanReboot
```

两个 `pkcheck` 都应为 `exit=0`；`CanReboot` 应返回 `s "yes"`。后者检查当前调用进程，因此这里只适用于上述账号级规则，不替代 Agent PID 的权限检查。`challenge` 或 `Authorization requires authentication` 表示仍需要认证；检查规则账号、加载错误和实际服务用户，不要用 `sudo pkcheck` 检查 root 自身来证明普通用户有权限。

**5. 验收与回退。** 完成以上步骤再使用本文末尾的真实重启请求。先保存 `/proc/sys/kernel/random/boot_id`，重启后应发生变化，Agent 自启并恢复 Cloud 连接，操作最终为 `succeeded`。HTTP 202、SSH 断开、Agent 进程重启本身都不是系统重启成功的充分证据。权限失败时当前实现返回 `execution_failed`；不要将它直接判定为程序崩溃或服务被停止。

停用远程重启时，将实际配置中的 `allow_remote_reboot` 改为 `false` 并重启 Agent。撤销本次账号授权可删除 `/etc/polkit-1/rules.d/49-agent-reboot.rules`；若安装前存在同名规则，应恢复备份。再次进行只读权限检查确认回退结果。
