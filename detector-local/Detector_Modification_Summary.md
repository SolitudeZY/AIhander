# Detector 代码修改与优化总结

本文档总结了在本次开发与调试过程中，针对 `detector.py` 所进行的核心代码修改与优化，主要解决了拉流稳定性、实时性、告警逻辑以及环境适配等问题。

## 1. 环境与部署适配
* **修复 OpenCV 依赖**：将运行环境从全局 Python 切换至板端带有完整依赖的 Conda 环境 (`/home/kickpi/miniconda3/envs/rknn/bin/python`)，解决了 `opencv-python-headless` 缺失导致无法拉流的问题。
* **模型路径修正**：修改了 `moduleName` 的加载路径逻辑，正确指向了 `../model/` 目录，确保动态下发配置时能准确找到模型文件。
* **时区硬编码**：移除了对底层操作系统时区的依赖，在生成 `time` 和 `alarmTime` 等时间戳时，强制指定使用东八区（UTC+8），保证云端接收到的时间准确无误。

## 2. 视频拉流稳定性优化
* **强制 TCP 传输**：针对 H.265 (HEVC) 视频流在 UDP 下容易丢包导致 `Could not find ref with POC` 解码报错的问题，通过环境变量 `OPENCV_FFMPEG_CAPTURE_OPTIONS` 强制 OpenCV 底层使用 TCP 协议拉流，消除了花屏和报错。
* **拉流失败指数退避**：加入了拉流失败后的指数退避重试机制（5s -> 10s -> 20s...最大60s），并在重试期间将通道状态标记为 `offline`，避免了无效通道导致的 FFmpeg 底层疯狂报错刷屏。
* **测试流拦截 (`isTest` 标记)**：针对测试用的无效流，在调用 `cv2.VideoCapture` 之前增加了轻量级的 TCP 端口连通性探测。若探测失败则静默拦截，杜绝了无意义的拉流尝试和日志污染。

## 3. 实时性与性能优化（核心架构调整）
* **独立抽帧线程 (`StreamReader`)**：彻底解决了由于 RKNN 推理速度慢于摄像头出帧速度而导致的“视频流缓存堆积（画面停留在过去）”问题。通过引入独立的抽帧线程，以最高速度清空 FFmpeg 缓冲区，确保推理主线程每次拿到的都是绝对实时的最新帧。
* **真实拉流 FPS 分离**：将 FPS 的计算逻辑从受阻于推理耗时的主循环中剥离，移至 `StreamReader` 线程中，使得云端状态广播 (`channelStatusChanged`) 能够准确上报摄像头原生的真实拉流帧率（如 25 FPS）。

## 4. 告警与图像分析逻辑重构
* **移除假告警，接入真实模型**：删除了原先定时发送测试图片的假告警逻辑，完全集成了 `infer_rknn.py` 的真实推理功能。只有当画面中真实检测到滑坡且置信度达标时，才会触发 `alarmDetected`，并加入了 60 秒的告警冷却时间防止刷屏。
* **真实的图像质量评估 (`pictureMetrics`)**：移除了原先的随机数生成，实现了一套基于 OpenCV 的轻量级图像质量统计算法：
  * **黑屏 (`black_screen`)**：基于灰度均值计算。
  * **严重模糊 (`blur`)**：基于拉普拉斯方差计算边缘信息。
  * **严重遮挡 (`occlusion`)**：基于标准差计算画面单调程度。
  * **亮度异常 (`brightness_abnormal`)**：基于均值的过高（过曝）或过低（过暗）计算。
