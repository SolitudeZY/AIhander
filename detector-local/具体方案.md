# 设备远程管理平台与模块化 Agent 具体方案

## 1. 目标与边界

本方案用 Go 实现云端管理服务（Cloud）与设备端 Agent 组成的远程管理闭环。Cloud 和 Agent 分别使用独立的 SQLite 数据库：Cloud 数据库保存设备注册、文件和升级任务等云端业务数据；Agent 数据库保存视频通道等设备本地运行配置以及检测程序产生的告警记录。两个数据库不共享文件、不跨网络直接访问，数据只能通过 HTTP/WSS 协议交换。后期 Cloud 数据库可迁移到 PostgreSQL，设备端 Agent 继续使用适合嵌入式部署的 SQLite。设备侧采用 `Agent Core + Agent Module` 架构：Agent Core 负责基础设施和强连接能力，业务功能通过跨语言模块扩展。系统实现：

- 设备通过一条主动建立的 WSS 控制长连接，每分钟上报状态（CPU、内存、磁盘、Agent 版本、在线状态）。
- 管理端通过控制长连接把升级任务即时下发给一个或多个设备。
- Agent 使用独立 HTTPS 文件连接下载升级包，支持断点续传并校验 SHA-256。
- Agent Core 内置远程 Terminal Shell，直接维护 PTY/ConPTY 与远程会话，避免终端再经过外部模块连接。
- Agent Core 提供轻量本地消息总线，独立 Agent Module 通过订阅、发布和请求响应与 Core 通信。
- 文件管理与当前阶段的固件/模型文件下发合并为 File Module，统一处理目录、传输、校验和原子落盘。
- 视频通道配置以 Detector 自身配置为权威数据源；Agent 连接 Detector 后主动读取一次完整配置，并在本地 SQLite 保存 Detector 已确认的镜像。Cloud 和 setUp 通过 Agent 查询和修改，不维护可反向覆盖 Detector 的配置副本。
- Cloud 和本地上位机 setUp 是同时存在的两套管理端：Agent 主动连接远端 Cloud，setUp 在实际终端上主动连接 Agent 提供的本地 WebSocket。
- setUp 功能参考 Cloud，保留现场所需的设备状态、通道、告警、单设备文件下发和 Terminal，精简云端批量编排与集中运维能力；发生冲突时 setUp 控制优先。
- 两套管理端均可查看设备、任务及执行状态，Agent 负责消息扇出和控制仲裁。

本期不实现标准 SSH/SFTP 服务、账号体系、真正的 A/B 分区切换和自动回滚；它们列入后续迭代。远程 Terminal 由 Agent Core 通过 PTY/ConPTY 提供，不对外开放 SSH 端口。Agent 主动建立到 Cloud 的 WSS；同时为同机 setUp 提供默认仅绑定 `127.0.0.1` 的本地 WebSocket。设备不需要暴露公网入站端口。

## 2. 总体架构

```text
┌────────────────────────────────────────┐       WSS/HTTPS        ┌────────────────────────────┐
│ Device：Agent Core                     │ =====================> │ Cloud：Go 管理平台         │
│ - Cloud 注册、鉴权、WSS 与重连          │  控制、配置、Terminal、状态│ REST API + WSS Hub         │
│ - Terminal Manager（PTY / ConPTY）      │                        │ Terminal Gateway          │
│ - Telemetry、Module Manager             │ <──── 文件传输 ───────> │ 文件存储 uploads/         │
│ - SQLite agent.db                      │       HTTPS/Range      │ SQLite firmware.db        │
│   └── Detector 已确认的通道配置镜像      │                        │ （后期可迁移 PostgreSQL）  │
│ - Agent Local Message Bus              │                        │ 设备、文件、升级任务等     │
│             │ 本地 WebSocket           │                        │ 不保存权威视频通道配置     │
│             ├── File Module            │                        │                            │
│             └── Other Module           │                        │                            │
└────────────────────────────────────────┘                        └────────────────────────────┘
```

本地 setUp 链路补充如下：

```text
Detector（WS 服务端） <── Agent 主动连接 ── Agent ──主动连接──> Cloud（远端 WS 服务端）
                                              ▲
                                              │ setUp 主动连接本地 WS
                                              │
                                      setUp（精简本地管理端）
```

Cloud 与 setUp 不互相代理。Agent 同时维护两条管理链路：Cloud 链路用于远程集中管理，setUp 链路用于现场本地管理。查询和状态上报可以并行；同一资源发生写冲突时，由 Agent 的统一调度器优先执行 setUp 命令。

### 2.1 WebSocket 端口与连接方向

| 端口 | WebSocket 服务端 | WebSocket 客户端 | 定位 |
|---|---|---|---|
| `8080` | Cloud | Agent | Cloud 管理控制端口，Agent 主动连接 |
| `8085` | Agent | setUp | Agent 本地管理端口，setUp 主动连接 |
| `8090` | Detector | Agent | Detector 检测端口，Agent 主动连接 |

三个端口必须按服务端归属理解：Cloud 监听 `8080`、Agent 监听 `8085`、Detector 监听 `8090`。Agent 同时承担两种角色：作为客户端连接 Cloud 和 Detector，作为服务端接受本机 setUp 连接。

当前 Demo 的 Cloud HTTP/WebSocket 共用 `8080`；生产部署可由网关映射为 HTTPS/WSS `443`。setUp 通过终端内部回环地址连接 Agent `8085`，Agent 连接 Detector `8090`。`8085` 默认不监听外部网卡，不要求公网 IP、端口映射或开放 SSH/FTP 入站端口。

独立 setUp 管理服务默认在 `127.0.0.1:8086` 提供自己的 HTTP 页面和浏览器接口。该端口属于 setUp 的展示层，不属于 Agent、Cloud、Detector 三条设备协议 WebSocket 端口。

管理平台、Agent Core 和 Agent Module 分别部署：

- `cmd/cloud`：云端管理 HTTP 服务、Cloud SQLite 持久化、升级文件存储和任务调度；后期只替换其数据访问实现即可迁移 PostgreSQL。
- `cmd/agent`：设备端 Agent Core，维护远程 WSS、Agent SQLite、视频通道配置、Terminal、Telemetry、本地消息路由和 Module 生命周期。
- `cmd/setup`：独立终端本地管理服务，自己提供页面、HTTP API、SQLite 和告警图片目录，并作为客户端主动连接 Agent 本地 WebSocket；功能参考 Cloud 但精简。
- `cmd/agent` 的 setUp 部分只监听 `8085` 协议 WebSocket和执行本地优先仲裁，不托管 setUp 管理页面。
- `modules/file`：File Module，负责目录、文件传输、SHA-256 校验、原子落盘和当前阶段的文件下发任务。
- 其他 Module：可以由不同团队、不同语言实现，只需遵守本地消息协议和 Module 清单。
- `internal`：Server、Agent Core 共用的数据模型、协议定义及工具函数。

## 3. 技术选型

| 范围 | 选型 | 理由 |
| --- | --- | --- |
| 语言与运行时 | Go 1.26.5 | 当前稳定补丁基线；单二进制部署，适合设备端和运维环境。 |
| HTTP 路由 | 标准库 `net/http` | Demo 依赖少、易维护。 |
| 控制长连接 | `github.com/coder/websocket` | 支持 Go `context`，用于 Agent→Cloud、setUp→Agent 和 Agent→Detector WebSocket。 |
| Agent 本地消息总线 | 本地 WebSocket + JSON 信封 | 无独立 Broker，跨语言简单；Agent Core 负责订阅、发布、请求响应和权限。 |
| Terminal | Windows ConPTY / Linux PTY | Agent Core 直接管理交互式 Shell、尺寸调整、会话重连和输出缓冲。 |
| Module 契约 | `module.json` + 版本化 Topic | 允许不同团队、语言和发布节奏，同时约束订阅、发布与能力。 |
| Cloud 数据库 | SQLite；后期 PostgreSQL | Demo 使用单文件部署；通过 Repository 隔离 SQL 方言，为云端多实例和高并发迁移 PostgreSQL。 |
| Agent 数据库 | `agent.db`（SQLite + `modernc.org/sqlite`） | 设备端单机嵌入式持久化、无独立数据库服务；纯 Go 驱动便于 ARM 交叉编译。 |
| 状态采集 | `github.com/shirou/gopsutil/v4` | 跨平台读取 CPU、内存和磁盘。 |
| 文件校验 | 标准库 `crypto/sha256` | 确保设备下载到的文件完整。 |
| 配置 | JSON 文件 + 命令行参数 | Demo 易理解，后续可切换 YAML/环境变量。 |

### Go 版本策略

- 开发、CI 与发布镜像统一固定为 Go `1.26.5`，并在每次 Go 安全补丁发布后升级至同一 `1.26.x` 最新补丁版。
- `go.mod` 使用 `go 1.26.0` 声明语言与工具链下限；构建环境以 `go env GOVERSION` 校验实际版本不低于 `1.26.5`。
- 设备端构建优先关闭 CGO（`CGO_ENABLED=0`），SQLite 使用纯 Go 的 `modernc.org/sqlite`，以降低 ARM、x86 与不同 Linux 发行版的部署差异。
- 正式 Agent 发布目标定为 `linux/arm64`；`windows/amd64` 仅用于本地开发和联调。
- Go 1.25 仅作为设备现有构建环境暂时不能升级时的兼容下限，不作为新功能开发或正式发布基线。

## 4. 设备信息

### 4.1 `device_id` 生成规则

Agent 启动时读取当前操作系统返回的网卡列表，以网卡 MAC 地址作为固定 `device_id`。当前实现规则如下：

1. 调用 Go `net.Interfaces()` 获取操作系统返回的网卡列表，保留其原始顺序，不按名称、IP、网卡类型或在线状态重新排序。
2. 若配置了 `device_interface`，按网卡名称进行不区分大小写的精确匹配，只检查该网卡；找不到或 MAC 无效时，Agent 报错并按注册重试周期继续重试，不自动换用其他网卡。
3. 若 `device_interface` 为空，从网卡列表开头依次检查，选择第一个有效网卡。
4. 有效网卡必须同时满足：不是回环网卡、MAC 地址长度为 6 字节、MAC 不是全零地址。
5. 网卡是否处于 `UP`、是否插网线、是否获得 IP 地址不参与选择，避免首选网卡临时断网时切换身份。
6. 选中网卡的 MAC 转为小写、冒号分隔的标准格式，并直接作为 `device_id`，例如 `d8:5e:d3:5e:88:40`。

多网卡设备默认选择操作系统返回的第一个有效网卡。若设备的网卡枚举顺序可能因系统升级、驱动或虚拟网卡变化而改变，应明确配置固定网卡：

```json
{
  "device_interface": "eth0"
}
```

Windows 可以填写实际网卡名称，例如 `以太网`；Linux 通常填写 `eth0`、`enp1s0` 等。设备更换网卡、修改硬件 MAC、启用 MAC 随机化，或操作系统改变首个有效网卡时，会产生新的 `device_id`，Server 会将其视为新设备。正式设备应使用硬件固定 MAC，并保持网卡枚举和 `device_interface` 配置稳定。

### 4.2 设备名称与注册信息

- `device_name` 只用于页面展示和运维识别，不参与设备身份计算；修改名称不会改变 `device_id`。
- Agent 每次启动都会使用当前 `device_id` 注册，上报 `device_name`、操作系统、CPU 架构和 Agent 版本。
- Server 已存在该 `device_id` 时，验证 Agent 保存的原设备令牌，验证通过后更新名称和其他设备信息，但保持令牌不变。
- Server 不存在该 `device_id` 时，创建新设备记录并签发设备令牌；Agent 将 `device_id` 和令牌保存到 `state_file`。
- 本地状态文件中的 `device_id` 与当前 MAC 不一致时，不复用旧令牌，而是按新设备注册。

因此，设备名称可以随时修改并始终对应同一个 MAC 设备；真正决定设备身份的是选中网卡的 MAC 地址。

## 5. 数据流

### 5.1 设备注册与心跳

1. Agent 启动时按“设备信息”章节的规则选择网卡，以小写冒号格式的 MAC 地址生成固定 `device_id`，并读取本地状态文件中的设备令牌。
2. Agent 调用 `POST /api/v1/agents/register`，上报设备名称、系统、CPU 架构和 Agent 版本。
3. 管理端创建或更新设备记录，返回 `device_token`。
4. 注册成功后，Agent 建立 `wss://<server>/api/v1/agents/connect`，并使用设备令牌完成连接鉴权。
5. Agent 每 60 秒在该 WSS 连接发送 `heartbeat` 消息，携带 CPU、内存、磁盘等当前状态。
6. 管理端更新 `devices.last_seen_at`，将状态写入 `device_metrics`；连续两个心跳周期未收到心跳即显示离线。

### 5.2 视频通道配置

视频通道配置属于设备本地运行配置，Detector 自身配置是权威数据源，Agent SQLite 只保存 Detector 最近一次确认的配置镜像。Cloud 和 setUp 只负责管理入口、协议转发和结果展示，不能在设备重连时使用管理端旧配置覆盖 Detector。

Agent 每次成功连接 Detector 后，主动发送一次 `channelList`。Detector 返回 `channelListResult` 后，Agent 在单个 SQLite 事务中用完整结果替换 `video_channels` 镜像；5 秒内没有收到响应时记录同步失败，但不得使用旧镜像反向覆盖 Detector。生产 Detector 应持久化自身配置；Detector Demo 当前只在进程内保存配置。

查询流程：

1. 页面调用 Cloud 的视频通道查询接口。
2. Cloud 确认设备在线，生成 `request_id`，通过该设备的 WSS 发送 `channelList`。
3. Agent 查询本地 SQLite 中最近一次由 Detector 确认的镜像，并通过带相同 `request_id` 的 `channelListResult` 返回完整配置及当前 `revision`。
4. Cloud 将结果直接返回页面。第一阶段不在 Cloud SQLite 保存完整视频通道配置；设备离线或请求超时时返回明确错误，不把历史数据伪装成实时配置。

新增、修改和删除流程：

1. 页面向 Cloud 提交新增、修改或删除请求；离线设备禁止操作。
2. Cloud 生成 `request_id`，通过 WSS 发送 `channelSet` 或 `channelDelete`。修改、删除应携带页面读取到的 `expected_revision`。
3. Agent 完成参数校验，并根据 SQLite 镜像预检 `expected_revision`；Agent 转发给 Detector 时不携带 `expected_revision`。
4. Detector 保存并应用配置，生成最终 `revision`，使用相同 `request_id` 返回 `channelSetResult` 或 `channelDeleteResult`。
5. Agent 最多等待 5 秒。只有 Detector 明确确认成功后，Agent 才在 SQLite 事务中更新或删除镜像，然后把结果返回 Cloud/setUp。
6. Detector 返回失败或 5 秒超时时，Agent 保持 SQLite 镜像不变，并返回“配置失败，请重试”。若预检发现 `expected_revision` 不一致，则返回冲突并要求管理端重新查询。

Agent 与 Detector 断线重连后，由 Agent 主动发送一次 `channelList` 刷新 SQLite 镜像，不执行“Agent 全量配置下发”。Agent 与 Cloud 断线重连后，Cloud 可以查询 Agent 镜像刷新页面，但不得执行“Cloud 全量配置下发”。Cloud 数据库丢失不影响 Detector 按自身配置运行。

当前阶段不持久化通道操作记录。Detector 使用固定 `channel_id` 执行 UPSERT 并维护 `revision`；`channelDelete` 删除不存在的通道时也按成功处理，使删除操作具备幂等性。Cloud/setUp 写操作失败或超时后应提示用户重试；重试前页面可重新查询 Agent 镜像确认当前配置。

setUp 对视频通道使用相同的 `channelList/channelSet/channelDelete` 消息，但通过 `8085` 本地连接直接请求 Agent。Cloud 和 setUp 查询可并行；同一 `channel_id` 的写命令发生冲突时，尚未开始的 setUp 命令优先。优先级不绕过 Agent 的 `expected_revision` 镜像预检，也不强制中断已经转发给 Detector 的 Cloud 操作。

### 5.3 告警记录与上报

1. 检测程序产生告警后，通过 Agent 本地接口或消息总线提交视频通道号、检测类型、置信度和告警时间。
2. Agent 将告警写入本地 SQLite，初始设置 `reported=0`、`reported_at=NULL`。
3. Agent 将告警分别通过 Cloud WSS 和 setUp 本地 WS 投递；任一管理端离线不得阻塞另一端。
4. Cloud 和 setUp 分别使用告警 rowId 幂等确认。Agent 已按 `target=cloud|setUp` 保存独立投递状态；收到某一端确认只更新该端状态，不能代替另一端确认。
5. 当前代码已有的 `reported/reported_at` 表示 Cloud 上报状态；实现 setUp 后应增加独立 outbox/投递状态。发送失败或确认超时时保持对应目标未上报，连接恢复后继续重试。
6. 检测程序不直接持有 Cloud 或 setUp 令牌，也不直接连接管理端；对 Agent SQLite 的写入统一经过 Agent Repository，避免多个进程依赖数据库内部结构。

### 5.4 文件/升级资源下发

1. 管理员调用上传接口，将固件包上传至管理平台 `data/uploads/`。
2. 管理端计算 SHA-256、记录文件元数据。
3. 管理员指定设备 ID 列表并从在线 Agent 加载目标目录；页面只选择目录，不手写目标文件名。
4. 管理端为每台目标设备创建一个独立的任务项；在线设备立即通过其 WSS 控制通道收到 `task.assign` 消息，离线设备在重连后补发。
5. Agent Core 将远程任务转换为本地 `command.file.deploy.v1`，交给订阅该 Topic 的 File Module。
6. File Module 通过独立 HTTPS 请求下载文件到 `.part` 临时文件；支持 `Range` 断点续传。
7. File Module 校验 SHA-256，通过后以原始文件名原子移动到所选目录，并发布进度或结果事件。
8. Agent Core 将 `event.file.progress/completed/failed` 转换为 Server 的任务状态并通过 WSS 上报。

setUp 文件下发复用 `directory.list`、`task.assign` 和 `task.status`，但只需面向当前设备，不创建 Cloud 的多设备 deployment。setUp 可在本机提供 HTTP Range 文件服务；Agent 必须根据任务来源解析下载 URL，不能把 setUp 的 `127.0.0.1` 下载地址重写到 Cloud。

### 5.5 通道职责

| 通道 | 协议与生命周期 | 承载内容 | 设计原因 |
| --- | --- | --- | --- |
| Cloud 控制面 | Agent 主动建立一条长期 WSS | 注册、心跳、视频通道查询/修改、告警上报、任务下发、进度和 Terminal | 远程集中管理，连接断开后 Agent 自动重连。 |
| setUp 控制面 | Agent 本地 WS 服务，setUp 主动连接 | 本地设备状态、通道查询/修改、告警、单设备任务和 Terminal | 与 Cloud 业务命令复用；冲突时本地 setUp 优先。 |
| 文件面 | 每次升级按需建立 HTTPS 连接 | 文件下载、Range 续传、限速、哈希校验 | 大文件不会阻塞心跳、任务或终端；直接复用 HTTP 的续传和超时能力。 |
| Module 总线 | Agent Core 本机 WebSocket | Module 注册、Topic 订阅、命令、事件、请求响应 | 不额外部署 Broker，允许 Go、Python、C++、C# 等模块接入。 |
| Terminal 数据面 | 与控制面共用 Agent WSS，通过二进制逻辑通道复用 | Shell 输入输出、序号、确认、断线补发 | 第一阶段减少连接数量，通过应用层队列、分块和流量控制避免阻塞；达到拆分条件后再使用独立 Terminal WSS。 |

禁止把整包固件数据直接写入普通 WSS 消息流。WebSocket 是有序流，弱网下的大文件可能挤占队列并造成心跳、任务取消和远程终端卡顿。

### 5.6 当前文件下发约定

- 上传包可以是任意文件；Demo 不限定固件格式。
- `target_path` 表示相对于 Agent `allowed_target_dir` 的目录，不包含文件名。
- File Module 使用上传时的原始文件名保存，例如目标目录为 `models`、文件为 `model.rknn`，最终路径为 `<allowed_target_dir>/models/model.rknn`。
- File Module 必须限制目录穿越、绝对路径、符号链接或 Windows Junction 越界。
- 当前阶段的“升级任务”只负责文件下载、校验和落盘，不执行真正的安装、重启和回滚。
- 当后续出现包签名、版本检查、安装、A/B 切换、重启验证和回滚时，再拆分独立 Upgrade Module；File Module 继续只提供文件能力。

File Module 在部署上是一个独立进程，在代码内部划分 Directory Service、Transfer Service 和 Deployment Service，既减少进程数量，又保持未来拆分边界。

## 7. 数据库分离与表设计

系统存在两个物理独立的数据库：

- **Cloud 数据库**：位于云端服务器，Demo 使用 `./data/firmware.db`；保存设备注册、指标、文件、发布任务及逐设备任务。后期可迁移为 PostgreSQL。
- **Agent 数据库**：数据库文件名统一固定为 `agent.db`，默认放在 Agent 可执行文件同级的 `db` 目录，即 `<Agent 程序目录>/db/agent.db`；每台设备各自保存自己的文件，用于持久化该设备的视频通道配置和检测告警记录，并持续使用 SQLite。启动时由 Agent 自动创建 `db` 目录。

Cloud 和 Agent 不使用 SQLite 文件复制、共享磁盘或远程挂载进行同步。Cloud 只能通过带设备身份鉴权的 WSS 消息读取和修改 Agent 数据。业务代码应分别定义 `CloudRepository` 和 `AgentRepository`，禁止复用一个 Repository 后误把两个数据库当成主从副本。

### 7.1 Cloud 数据库

```sql
CREATE TABLE devices (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  token_hash TEXT NOT NULL,
  os TEXT,
  arch TEXT,
  agent_version TEXT,
  created_at DATETIME NOT NULL,
  last_seen_at DATETIME NOT NULL
);

CREATE TABLE device_metrics (
  device_id TEXT PRIMARY KEY REFERENCES devices(id),
  updated_at DATETIME NOT NULL,
  cpu_percent REAL NOT NULL,
  memory_total_gb REAL NOT NULL,
  memory_used_gb REAL NOT NULL,
  memory_used_percent REAL NOT NULL,
  disk_total_gb REAL NOT NULL,
  disk_used_gb REAL NOT NULL,
  disk_used_percent REAL NOT NULL
);

CREATE TABLE files (
  id TEXT PRIMARY KEY,
  original_name TEXT NOT NULL,
  storage_name TEXT NOT NULL UNIQUE,
  size_bytes INTEGER NOT NULL,
  sha256 TEXT NOT NULL,
  created_at DATETIME NOT NULL
);

CREATE TABLE deployments (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  file_id TEXT NOT NULL REFERENCES files(id),
  version TEXT,
  target_path TEXT NOT NULL,
  target_is_directory INTEGER NOT NULL DEFAULT 1,
  install_command TEXT NOT NULL,
  created_at DATETIME NOT NULL
);

CREATE TABLE deployment_tasks (
  id TEXT PRIMARY KEY,
  deployment_id TEXT NOT NULL REFERENCES deployments(id),
  device_id TEXT NOT NULL REFERENCES devices(id),
  status TEXT NOT NULL,
  progress INTEGER NOT NULL DEFAULT 0,
  message TEXT,
  result_output TEXT,
  claimed_at DATETIME,
  started_at DATETIME,
  finished_at DATETIME,
  UNIQUE(deployment_id, device_id)
);

CREATE TABLE alarm_records (
  device_id TEXT NOT NULL REFERENCES devices(id),
  agent_row_id INTEGER NOT NULL,
  channel_id TEXT NOT NULL,
  detection_type TEXT NOT NULL,
  confidence REAL NOT NULL,
  alarm_time DATETIME NOT NULL,
  image_path TEXT NOT NULL DEFAULT '',
  received_at DATETIME NOT NULL,
  PRIMARY KEY(device_id, agent_row_id)
);

CREATE INDEX idx_tasks_device_status ON deployment_tasks(device_id, status);
```

Cloud 数据库不创建作为权威配置源的 `video_channels` 表。若后续确有离线展示、搜索或审计需求，可以增加名称明确的 `video_channel_snapshots` 只读快照表，并强制记录 `source_revision`、`synced_at` 和 `stale`；快照只能由 Agent 查询结果更新，绝不能在 Agent 重连时反向下发。

Cloud 的 `alarm_records` 是告警接收结果，不是设备配置。`device_id + agent_row_id` 用于对 Agent 断线重报进行幂等去重；`image_path` 保存 Cloud 告警图片目录下的相对地址。Cloud 成功提交记录和图片后才向 Agent 返回确认，两端不是 SQLite 文件同步关系。

`device_metrics` 每台设备只保存一条最新记录：首次心跳执行 `INSERT`，后续按 `device_id` 执行 UPSERT。CPU 和百分比保留两位小数，内存和磁盘容量以 GB 保存，`updated_at` 只保留到秒。若未来需要指标历史趋势，应单独接入 Prometheus、TimescaleDB 等时序系统，不在该表持续追加历史记录。

`deployments.install_command` 是兼容已有 Demo 数据库的保留列，当前 File Module 下发流程不使用该字段；真正的安装命令和回滚策略应归属未来 Upgrade Module。

### 7.2 Agent 数据库

```sql
CREATE TABLE agent_meta (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at DATETIME NOT NULL
);

CREATE TABLE video_channels (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  rtsp_url TEXT NOT NULL,
  model_name TEXT NOT NULL DEFAULT '',
  enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1)),
  transport TEXT NOT NULL DEFAULT 'tcp',
  revision INTEGER NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL
);

CREATE TABLE alarm_records (
  channel_id TEXT NOT NULL,
  detection_type TEXT NOT NULL,
  confidence REAL NOT NULL,
  alarm_time DATETIME NOT NULL,
  image_path TEXT NOT NULL DEFAULT '',
  reported INTEGER NOT NULL DEFAULT 0 CHECK (reported IN (0, 1)),
  reported_at DATETIME
);

-- 双管理端投递状态；当前代码已实现。
CREATE TABLE alarm_delivery_state (
  alarm_rowid INTEGER NOT NULL,
  target TEXT NOT NULL CHECK (target IN ('cloud', 'setUp')),
  reported INTEGER NOT NULL DEFAULT 0 CHECK (reported IN (0, 1)),
  reported_at DATETIME,
  PRIMARY KEY(alarm_rowid, target)
);

CREATE INDEX idx_alarm_delivery_pending
  ON alarm_delivery_state(target, reported, alarm_rowid);

CREATE INDEX idx_alarm_records_pending
  ON alarm_records(reported, alarm_time);
```

- `video_channels` 是 Detector 已确认配置的本地镜像，不是权威源；RTSP 地址可能包含账号密码，数据库文件权限必须限制为 Agent 运行账号可读写。
- `revision` 由 Detector 在每次有效修改时生成，Agent 按 Detector 返回值原样保存，并用于管理端写入前的版本预检查。
- 通道的 `status`、`input_fps` 和瞬时错误属于运行状态，默认保存在内存并由 Agent 主动上报，不与配置字段混写。需要断电诊断时可另建运行快照表，但不能改变配置权威关系。
- `alarm_records.image_path` 保存相对于 `agent.db` 所在目录的告警图片地址，图片文件不作为 BLOB 写入 SQLite。
- 当前 `reported/reported_at` 保持 Cloud 上报状态以兼容已有代码。`alarm_delivery_state` 分别保存 `cloud`、`setUp` 两个目标的投递确认，setUp 确认不能提前完成 Cloud 状态。
- 新告警为两个目标各创建一条未投递状态；只有收到对应管理端成功确认后才更新该目标的 `reported=1` 和实际确认时间。索引用于按目标和告警时间扫描待上报记录。
- 表中不额外增加业务 ID，Agent Repository 使用 SQLite 隐式 `rowid` 完成本地记录定位与上报状态回写；`rowid` 不作为跨设备的告警业务编号。
- 已上报告警需要配置保留期限并定期清理，避免设备磁盘无限增长；未上报告警不得仅因超期而删除。具体保留天数和最大磁盘占用在部署配置中确定。
- 当前阶段不设置通用操作记录表。通道写操作通过固定 `channel_id`、UPSERT、`revision` 和幂等删除保证可安全查询与重试。
- Agent 启动时先执行本地 schema migration，再启动 setUp 本地 WS、视频模块和 Cloud WSS；迁移失败时不得用空数据库覆盖或删除原数据库。

## 8. Agent 设计

### 8.1 能力边界

Agent Core 是设备侧唯一的平台基础进程，负责：

- 设备注册、令牌、Server WSS、重连和消息编解码。
- 在 `127.0.0.1:8085` 提供 setUp 管理 WebSocket，完成独立鉴权、消息路由和断线清理。
- 向 Cloud 与 setUp 扇出心跳、通道状态和告警，并按目标保存告警确认状态。
- 对 Cloud、setUp 控制命令统一排队和资源仲裁，冲突时保障 setUp 本地控制优先。
- Agent SQLite 的迁移、Detector 通道配置镜像、revision 预检查、告警记录及断线补报。
- 心跳、CPU、内存、磁盘和 Agent/Module 状态上报。
- 内置 Terminal Manager，直接管理 Windows ConPTY 或 Linux PTY；Terminal 不拆为外部 Module。
- 本地消息路由、Module 注册、Topic 权限、请求响应、超时和健康检查。
- Module 进程启动、停止、重启退避和能力汇总。

外部 Module 不直接连接 Server，不读取设备令牌，也不写 Agent Core 数据库。第一阶段只设置一个 File Module：

```text
File Module
├── Directory Service：目录加载、属性、创建、重命名、删除
├── Transfer Service：HTTPS 上传/下载、Range、限速、进度
└── Deployment Service：任务接收、SHA-256、.part、原子落盘
```

若未来真正实现安装、版本切换、设备重启、健康验证和回滚，再新增 Upgrade Module，通过版本化消息向 File Module 请求已准备好的本地文件。

### 8.2 轻量本地消息总线

Agent Core 自带轻量消息中心，不部署 NATS、MQTT 等额外 Broker。Agent Module 作为独立进程，通过仅监听 `127.0.0.1` 的本地 WebSocket 连接 Core，因此允许不同人员使用 Go、Python、C++、C# 或其他语言开发。

```text
Server <--WSS/HTTPS--> Agent Core <--Local WebSocket--> File Module / Other Module
```

统一消息信封：

```json
{
  "id": "msg-001",
  "type": "command",
  "topic": "command.file.deploy.v1",
  "source": "agent-core",
  "target": "files",
  "correlation_id": "",
  "timestamp": "2026-08-11T10:30:25Z",
  "payload": {}
}
```

消息类型及语义：

| 类型 | 语义 | 示例 |
| --- | --- | --- |
| `command` | 独占消费，只允许一个 Module 处理 | `command.file.deploy.v1` |
| `event` | 广播，可由多个 Module 订阅 | `event.system.disconnected.v1` |
| `request/response` | 通过 `correlation_id` 关联并设置超时 | `request.file.directories.v1` |
| `ack` | Module 确认已接收关键命令 | 固件/文件任务接收确认 |

Topic 必须版本化，修改字段含义、单位或删除字段时升级版本。Core 根据 `module.json` 强制限制每个 Module 可订阅和发布的 Topic；独占 Topic 出现多个订阅者时拒绝后注册者。

### 8.3 Module 注册与生命周期

每个 Module 提供清单：

```json
{
  "id": "files",
  "version": "1.0.0",
  "protocol_version": "1",
  "executable": "file-module.exe",
  "auto_start": true,
  "auto_restart": true,
  "subscriptions": [
    "command.file.deploy.v1",
    "request.file.directories.v1"
  ],
  "publications": [
    "event.file.progress.v1",
    "event.file.completed.v1",
    "event.file.failed.v1",
    "system.module.health.v1"
  ]
}
```

Core 启动 Module 时通过环境变量传递本地连接地址、Module ID 和一次性令牌。Module 连接后的第一条消息必须是 `module.register`；Core 校验其声明与清单一致后才接受订阅。Module 每 5 秒发送健康心跳，连续 3 次缺失即标记离线；Core 按指数退避重启，达到最大次数后禁用并上报 Server。

每个 Module 使用独立、有界发送队列。文件内容不进入消息总线，总线只传文件 ID、URL、目录、文件名、SHA-256、进度和结果；文件内容继续走 HTTPS。

### 8.4 Terminal Shell

Terminal 是 Agent Core 内置组件，在代码上保持独立 `internal/agent/terminal` 包，在部署和进程上与 Core 一体。链路为：

```text
Browser xterm.js <--WSS--> Server Terminal Gateway <--WSS--> Agent Core Terminal Manager <--PTY--> Shell
```

Terminal 会话与具体网络连接分离，使用 `session_id` 标识，支持 `attached`、`detached`、`expired`、`exited`、`closed` 状态。短暂断线时 PTY 继续运行，在宽限时间内通过输出序号和有限环形缓冲区重新绑定；超过宽限时间后关闭 PTY。Shell 输入采用 at-most-once，避免重连时重复执行命令。

第一阶段每台 Agent Core 只维护一条远程 WSS，Terminal 控制、输入输出与心跳、任务状态在同一连接上逻辑复用。消息必须包含 `channel`；Terminal 消息还必须包含 `session_id` 和连续 `sequence`：

```json
{
  "channel": "terminal",
  "type": "terminal.output",
  "session_id": "terminal-001",
  "sequence": 186,
  "data": "..."
}
```

逻辑通道划分：

| Channel | 内容 | 编码 |
| --- | --- | --- |
| `control` | 心跳、任务、Module 状态、Terminal 打开和关闭 | JSON 文本帧 |
| `terminal-control` | 尺寸调整、挂接、脱离、ACK、退出状态 | JSON 文本帧 |
| `terminal-data` | Shell 输入和输出 | WebSocket 二进制帧 |

单连接复用必须遵守以下约束：

- Agent Core 只有一个远程 WSS Writer，业务 goroutine 不得直接写连接。
- Writer 使用 `critical`、`control`、`terminal` 三个有界队列，发送优先级依次降低。
- Terminal 输出按 4～16 KB 分块，每发送一个数据块后重新检查高优先级控制队列。
- 每个 Terminal 会话使用 1～4 MB 有界环形缓冲，所有会话设置总内存上限。
- Server 使用 `ack_sequence` 确认已处理输出；Agent 限制未确认输出窗口，窗口满后暂停 Terminal，不影响控制消息。
- 第一阶段每台设备最多 2 个 Terminal 会话，并配置单会话和单设备输出速率上限。
- 文件内容始终通过 HTTPS 传输，禁止通过该 WSS 发送大文件。

WebSocket 底层是有序 TCP 流，已经写入 Socket 的 Terminal 数据无法被后续心跳抢占，因此分块、窗口和速率限制是单连接方案的必要条件。出现以下任一情况时，再将 `terminal-data` 路由到独立 Terminal WSS，现有 `channel/session_id/sequence` 上层协议保持不变：

- 每台设备需要 3 个以上并发终端。
- 经常运行持续或大量输出命令。
- 弱网下控制消息延迟或 Agent 被误判离线。
- Terminal 需要独立带宽、审计录制或文件传输能力。

### 8.5 局域网外部 Web 对接 Terminal

后续若需要将 Terminal 提供给同一局域网内的独立 Web 页面，外部 Web 不直接连接 Agent Core，也不要求设备开放 Terminal、SSH 或其他入站端口。所有连接仍由 Server 中转：

```text
局域网 Web（xterm.js） <--WebSocket--> Server Terminal Gateway <--现有 Agent WSS--> Agent Core Terminal Manager <--PTY/ConPTY--> Shell
```

外部 Web 只需要设备 ID，并建立一条 WebSocket：

```text
ws://server:8080/api/v1/terminal/connect?device_id=device-001
```

若 Server 启用 HTTPS，则使用：

```text
wss://server/api/v1/terminal/connect?device_id=device-001
```

连接流程保持简单：

1. Web 连接 Server Terminal Gateway，并在第一条消息提交局域网共享 Token。
2. Server 校验来源网段、Web Origin、共享 Token 和目标设备在线状态。
3. Server 为本次连接生成内部 `session_id`，通过现有 Agent WSS 发送 `terminal.open`。
4. Agent Core 创建 PowerShell、CMD 或 Bash 的 PTY/ConPTY，并回复 `terminal.opened`。
5. Server 在外部 Web 与 Agent Core 之间转发输入、输出和尺寸调整。
6. 外部 WebSocket 断开后，Server 立即发送 `terminal.close`，Agent Core 关闭 PTY。

外部 Web 与 Server 第一版只定义以下 JSON 消息：

```json
{"type":"auth","token":"internal-terminal-token"}
{"type":"input","data":"Get-Process\r"}
{"type":"output","data":"..."}
{"type":"resize","cols":120,"rows":35}
{"type":"close"}
{"type":"error","code":"DEVICE_OFFLINE","message":"device is offline"}
```

Server 与 Agent Core 之间继续使用第 7.4 节定义的单 WSS 逻辑通道，外部 Web 不感知 `channel`、`session_id`、消息优先级和 Module 协议，也不能获得设备 Token。

为控制第一阶段复杂度，局域网外接 Terminal 明确限制为：

- 每台设备只允许一个外部 Terminal 会话。
- WebSocket 断开即关闭 PTY，不实现断线恢复和输出补发。
- 不保存 Terminal 输出，不支持多人共同输入和只读旁观。
- Terminal 输入输出第一版使用 JSON；出现性能压力后再升级为二进制帧。
- 文件上传下载继续使用 HTTP/HTTPS，不通过 Terminal WebSocket 传输。
- Agent 或 Terminal 不可用时立即返回明确错误，不创建等待中的会话。

即使只在局域网使用，也至少启用以下保护：

```json
{
  "terminal_shared_token": "replace-with-internal-secret",
  "terminal_allowed_cidrs": ["192.168.1.0/24"],
  "terminal_allowed_origins": ["http://192.168.1.20"]
}
```

- Terminal Gateway 只允许配置的局域网网段访问。
- WebSocket Upgrade 校验 `Origin`，不允许任意网页连接。
- 共享 Token 只用于外部 Terminal Gateway，不能作为设备 Token 使用。
- Server 日志记录来源 IP、设备 ID、连接和断开时间，但默认不记录 Shell 输入输出。

独立 Web 推荐使用 `xterm.js`，只需负责WebSocket连接、输入发送、输出显示和窗口尺寸上报；Server负责设备路由和Terminal生命周期。后续确实出现多用户、断线恢复或审计录制需求时，再扩展会话票据、ACK和输出缓冲，不提前增加第一版复杂度。

### 8.7 并发模型

- Agent Core 的远程 WSS 使用一个 Reader 和一个统一 Writer；Writer 按 `critical > control > terminal` 调度逻辑通道，不直接执行耗时业务。
- 视频通道镜像和告警记录读写统一经过 Agent Repository；通道写操作由统一仲裁器串行转发 Detector，使用 `expected_revision` 预检，收到 Detector 确认后再以 SQLite 事务更新镜像。
- 每个 Module 连接拥有独立读循环、写队列和健康状态；慢 Module 不得阻塞 Core 或其他 Module。
- File Module 内部限制传输并发，并按任务 ID 去重；下载使用独立 HTTPS、`.part` 和 `Range`。
- Terminal 每会话独立 PTY 读写循环、输出序号、ACK 窗口和有界环形缓冲，不进入普通 Module 消息队列，但由统一 WSS Writer 发送。
- 控制、任务状态的优先级高于 Terminal 输出和文件进度；遥测允许覆盖旧值，只保留最新状态。

### 8.8 CPU 采集注意点

CPU 使用率必须取两次 CPU 时间差计算，首次采集可能为 0；Agent 启动后先预热一次。磁盘指标采集允许配置根目录，默认采集允许下发目录所在分区。

## 9. 管理端设计

### 9.1 Cloud 管理端

- 默认监听 `:8080`，工作目录为 `./data`。
- Cloud SQLite 数据库：`./data/firmware.db`，仅保存云端业务数据；后期通过 Cloud Repository 将该库替换为 PostgreSQL，不改变 Agent 数据库和 WSS 配置协议。
- 视频通道 HTTP Handler 不直接查询 Cloud SQLite，而是使用 `request_id` 通过 WSS Hub 请求指定在线 Agent；Cloud 维护有界的在途请求表，并在超时、断线时立即返回明确错误。
- Agent 重连 Cloud 后 Cloud 可拉取通道列表，禁止从 Cloud 数据库执行全量通道配置恢复；Agent 重连 Detector 后由 Agent 向 Detector 拉取真实配置。
- 文件保存目录：`./data/uploads`，存储名采用 `完整原文件名.yyyyMMdd_HHmmss`，例如 `model.rknn.20260811_103025`；同一秒同名文件追加 `_2`，数据库仍使用随机文件 ID 建立稳定关联。
- 上传时限制最大文件大小（Demo 默认 512 MB），并在写入时计算 SHA-256。
- 创建任务时，在一个事务中创建 `deployments` 与全部 `deployment_tasks`。
- 任务分配采用事务：创建后保持 `pending`；在线设备收到 `task.assign` 后回传 `downloading`，管理端才记录 `claimed_at`。断线或超时的 `pending/downloading` 任务可安全重发，Agent 以 `task_id` 做幂等去重。

### 9.2 本地 setUp 管理端

- **定位**：setUp 是参考 Cloud 功能实现的精简本地管理端，面向现场操作、设备调试和外网中断时的本机管理，不是 Cloud 代理，也不是 Agent Module。
- setUp 与 Agent 部署在同一实际终端；Agent 默认仅监听 `127.0.0.1:8085`，setUp 作为 WebSocket 客户端主动连接该端点。
- Agent→Cloud 与 setUp→Agent 两条连接同时存在。Cloud 不经过 setUp，setUp 也不持有 Cloud 设备令牌。
- setUp 与 Cloud 共用 Agent 业务命令和字段，setUp 下行信封使用区分大小写的 `_from=setUp`；Agent 不为本地管理复制第二套通道协议。
- setUp 不直接读取 `agent.db`。需要可靠确认告警时，使用自己的轻量数据库和图片目录保存最近告警；该数据库不是 Agent 配置副本。
- Agent 将心跳、通道状态和告警分别扇出到两端。告警按 `setUp/cloud` 分别记录投递与确认状态，任一端离线不阻塞另一端。
- Agent 对两端写命令统一串行仲裁。同一通道、目标文件路径或本地控制资源冲突时，尚未执行的 setUp 命令优先；已转发 Detector 的配置请求、已开始的 SQLite 事务或原子落盘不强制中断。
- setUp 优先不绕过 `expected_revision`。本地命令遇到版本变化仍应重新查询并由现场用户确认。
- setUp 连接常驻不代表永久锁住 Cloud；只在实际冲突的资源和操作周期内持有本地优先权，非冲突查询和操作可继续执行。
- 当前仓库已实现独立 `cmd/setup` 管理服务，以及 Agent `8085` 本地协议 WebSocket、双端扇出、告警双目标投递与控制仲裁；单设备文件下发暂未加入 setUp 页面。详细交互以 [`交互文档.md`](./交互文档.md) 为准。

setUp 功能以 Cloud 为参考，按以下范围精简：

| 功能 | setUp | 与 Cloud 的差异 |
|---|---|---|
| 设备状态与心跳 | 保留 | 主要展示当前终端，不做大规模设备汇总 |
| 视频通道查询和配置 | 保留 | Detector 为权威源，Agent SQLite 为确认镜像 |
| 实时状态、四项检测值和截图 | 保留 | 本地内存展示，不做长期趋势统计 |
| 告警接收、图片和最近记录 | 保留 | 独立于 Cloud 确认，可采用较短本地保留期 |
| 目录查询和文件下发 | 保留 | 只需支持当前设备或单设备任务，不做批量 deployment |
| Terminal | 保留 | 用于本机维护，发生资源冲突时优先于 Cloud 远程会话 |
| 多设备批量发布与重派 | 精简/不提供 | 由 Cloud 负责 |
| 跨区域访问、集中报表和长期编排 | 不提供 | 由 Cloud 负责 |

setUp 不保存可反向覆盖 Detector 的权威视频通道副本。页面缓存失效、写操作超时或 revision 冲突时，必须重新通过 `channelList` 查询 Agent 的确认镜像，再由现场用户确认操作。

## 11. 演示验收流程

1. 启动管理端：`go run ./cmd/cloud -listen :8080 -data-dir ./data`。
2. 启动两个 Agent Core，确认各自的 File Module 完成注册并处于健康状态。
3. 调用 `GET /api/v1/devices`，确认两台设备在线且已有 CPU、内存、磁盘数据。
4. 上传一个升级脚本或测试文件，保存返回的 `file_id`。
5. 创建一个包含两台设备的 deployment，确认两台在线 Agent Core 收到任务并路由为 `command.file.deploy.v1`。
6. 两台 File Module 使用独立 HTTPS 下载、校验并落盘；查询 deployment，确认任务均为 `succeeded`。
7. 在下载中断开网络后恢复，确认 Agent 经 `Range` 续传并且控制连接重连后仍能上报状态。
8. 故意上传哈希不匹配或执行返回非零的脚本，确认任务为 `failed` 且保留错误信息。
9. 通过 Cloud 新增、修改、查询和删除视频通道，确认 Detector 成功响应后 Agent SQLite 才更新镜像，Cloud SQLite 中不存在权威通道记录。
10. 重启 Agent 并重新连接 Detector，确认 Agent 主动读取 Detector 配置并替换 SQLite 镜像，不会把旧镜像反向下发给 Detector。
11. 断开设备网络，确认设备继续使用本地配置运行；Cloud 查询和修改返回明确的设备离线错误。
12. 在设备离线时产生告警，确认告警以 `reported=0` 写入 Agent SQLite；恢复连接并收到 Cloud 确认后，确认更新为 `reported=1` 且 `reported_at` 有值。
13. 启动独立 `setup.exe`，浏览器打开 `http://127.0.0.1:8086/`，确认 setUp 后端以 `_from=setUp` 主动连接 Agent `8085`，同时 Cloud WSS 保持在线。
14. 分别从 setUp 和 Cloud 查询通道，确认两端都从 Agent 权威配置得到结果；同时修改同一通道时确认 setUp 优先，Cloud 收到明确冲突结果。
15. 产生一条 Detector 告警，确认 Agent 分别投递给 setUp 和 Cloud，并在两个目标的确认状态中独立记录成功。
16. 断开外网，确认 setUp 仍可查看状态、管理通道、查看告警和使用本地 Terminal；恢复外网后 Cloud 自动重连且不会覆盖 setUp 已提交的最新 revision。

## 14. 特殊情况处理

### 14.1 下发视频通道配置后通道无流

Cloud 或 setUp 下发 `channelSet` 时，Detector 已初始化且连接正常，但 Detector 中不存在该 `channel_id` 的配置，Detector 应将 `channelSet` 按 UPSERT 处理：创建通道、生成从 `1` 开始的 `revision`，并使用原 `request_id` 返回 `channelSetResult`。配置成功只表示 Detector 已保存并开始应用配置，不表示 RTSP 视频流已经连接成功。

Detector 创建配置成功后，应先返回同步配置结果：

```json
{
  "_from": "detector",
  "cmd": "channelSetResult",
  "time": "2026-08-24T10:00:00+08:00",
  "values": {
    "requestId": "原请求 ID",
    "operate": true,
    "channelId": "CH-03",
    "channel": {
      "channelId": "CH-03",
      "name": "视频通道 3",
      "enabled": true,
      "rtspUrl": "rtsp://192.168.1.112/ch1",
      "transport": "tcp",
      "moduleName": "landslide.rknn",
      "revision": 1
    },
    "revision": 1,
    "status": "stopped"
  }
}
```

Agent 收到成功结果后，把 Detector 返回的完整 `channel` 和 `revision` 写入本地 SQLite 镜像，再向 Cloud/setUp 确认配置成功。此处的 `status=stopped` 是配置应用阶段的初始状态，不能作为视频流在线的判断依据。

Detector 随后负责连接 RTSP 地址并检测是否持续收到有效视频帧。连接失败、握手或鉴权失败、拉流超时，或者连接成功但在规定时间内没有收到有效视频帧，都按“通道无流”处理。Detector 应主动发送 `channelStatusChanged`，不得把配置已保存回滚为配置失败：

```json
{
  "_from": "detector",
  "cmd": "channelStatusChanged",
  "time": "2026-08-24T10:00:05+08:00",
  "values": {
    "operate": true,
    "channelId": "CH-03",
    "revision": 1,
    "status": "offline",
    "inputFps": 0,
    "observedAt": "2026-08-24T10:00:05+08:00",
    "err": "视频流连接失败或未收到视频帧"
  }
}
```

无流状态按以下规则处理：

- `status` 固定为 `offline`，`inputFps` 固定为 `0`，`err` 应填写可以展示和排查的具体原因；无有效画面时不发送 `snapshot` 和 `pictureMetrics`。
- Agent 接收状态后更新内存中的通道运行状态，并将同一条 `channelStatusChanged` 分别转发给 Cloud 和 setUp；该状态不修改 Agent SQLite 中已经确认的通道配置和 `revision`。
- Cloud/setUp 页面应把“配置同步状态”和“视频运行状态”分开显示：配置仍为已应用，视频状态显示离线及错误原因，不能把无流误报为配置下发失败。
- Detector 应继续按本地重连策略尝试拉流。后续收到有效视频帧时，主动上报 `status=running`、实际 `inputFps`、最新 `observedAt`，并清空 `err`；Cloud/setUp 据此恢复在线展示。
- 通道配置为 `enabled=false` 时属于主动停用，应上报 `status=stopped`、`inputFps=0`，不能上报为 `offline`。
- 只有 Detector 无法保存或应用通道配置本身时，才返回 `channelSetResult` 的 `operate=false` 和具体 `err`；RTSP 暂时无流不影响已经成功生成的配置及其 `revision`。
